# DotaLens 项目立项书

版本：0.1  
日期：2026-09-03  
状态：已确认，自用精简版

## 1. 项目背景

Liquipedia 的 Dota 2 选手资料较完整，但信息分散在选手、战队和赛事页面中。用户很难快速完成“查一个选手是谁、效力过哪些队、参加过哪些比赛、取得过什么成绩”的连续查询。

DotaLens 将这些公开资料保存到本地，提供中文检索、筛选和选手履历视图。项目仅供个人使用，以功能够用、维护简单为首要原则。

## 2. 项目目标

首期产品解决三个问题：

1. 快速找到职业选手并查看可靠的个人资料。
2. 按时间查看选手效力战队与参加赛事的完整履历。
3. 按赛区、国籍、战队、赛事等级、年份和名次筛选选手及参赛记录。

完成标准：能够同步指定选手或一批选手，在本地通过昵称找到选手，并查看个人信息、战队经历和参赛记录；每条详情能返回 Liquipedia 来源链接。

## 3. 用户与典型场景

唯一目标用户是项目所有者本人：查询选手个人资料，查看其战队经历，以及按年份浏览参赛赛事、代表队伍、最终名次和奖金。

## 4. MVP 范围

### 4.1 包含

- 选手目录：昵称、实名、别名、国籍、出生日期、状态、位置、头像。
- 选手详情：当前战队、历史战队、职业状态、简介、外部账号、来源。
- 参赛履历：赛事、日期、赛事等级、参赛队伍、最终名次、赛果、奖金。
- 中英文关键词搜索及国籍、赛区、年份、战队、赛事等级筛选。
- 一个手动“同步数据”入口，并显示成功、失败和最近同步时间。
- 数据来源链接；必要时直接在本地数据库中修正数据。

### 4.2 暂不包含

- 实时比分、赛程推送和直播。
- 单局 KDA、英雄池、GPM/XPM、选手天梯分等高频技术统计。
- 预测、赔率、博彩和自动生成选手评价。
- 原图批量镜像；头像先采用合规的远程引用或经许可的缓存策略。
- 用户注册、权限、管理后台、公共 API、SEO、消息通知和多设备同步。
- 微服务、任务队列、Redis、对象存储和复杂监控。

比赛级统计建议在二期通过 OpenDota 或 STRATZ 接入，并用 Steam Account ID 做实体匹配。该数据和 Liquipedia 的百科履历应作为两个独立数据源维护。

## 5. 数据来源与合规方案

### 5.1 采集原则

Liquipedia 明确禁止自动访问非 API 的生成 HTML 页面。因此，不以 `Portal:Players` 页面 HTML 爬虫作为生产方案，而是：

1. 优先申请 LiquipediaDB API Key，用结构化接口获取选手、战队、赛事及关联数据。
2. 在 API Key 尚未批准时，仅用 MediaWiki API 做小规模技术验证。
3. 使用 `Category:Players`、页面分类或 API 提供的对象列表发现选手；`Portal:Players` 仅作为人工核对入口。
4. 请求使用项目专属 User-Agent，并包含仓库地址（或项目说明地址）和联系邮箱。
5. 强制限流、长周期缓存和增量更新，不重复拉取未变化的数据。

已知官方限制：LiquipediaDB API 需申请授权，限制为每小时最多 60 次请求；MediaWiki API 普通请求最多每 2 秒 1 次，`action=parse` 最多每 30 秒 1 次。正式开发前须再次核对获批账户中的最新文档。

### 5.2 许可与隐私

- Liquipedia 内容采用 CC BY-SA 3.0，页面和 API 输出中必须展示来源署名及原始链接。
- 若对原文做翻译或改编，保留许可证信息，并明确标识为派生内容。
- 仅存储自用所需的公开职业资料，不收集私人联系方式等敏感信息。
- 图片许可需单独核验，不能默认沿用文本许可结论。

## 6. 产品结构

### 6.1 页面

- 首页：搜索框、同步按钮和最近查看。
- 选手列表：简单筛选和分页。
- 选手详情：资料卡、战队履历、参赛履历、荣誉、数据来源。

### 6.2 选手详情的展示优先级

1. 昵称、实名、头像、国籍、年龄、位置、当前战队。
2. 最近参赛与代表队伍。
3. 按年份组织的完整赛事成绩。
4. 历史战队时间线与主要荣誉。
5. 来源、同步时间和数据完整性提示。

## 7. 技术方案

采用一个 TypeScript 单体应用：

- Web：Next.js，页面与服务端接口放在同一工程。
- 数据库：SQLite + Prisma，数据库文件可直接备份。
- 同步：由页面按钮或本地命令触发，应用内串行执行并遵守 API 限流。
- 运行：本机使用 `npm run dev`；需要常驻时再增加一个简单 Dockerfile。

### 7.1 数据链路

```text
Liquipedia API
      │ 限流、重试、缓存
      ▼
缓存文件 ──> 解析与字段映射 ──> SQLite ──> 本地 Web 页面
```

默认手动同步。若以后确实需要自动更新，再增加每天一次的本机定时任务。请求响应可按页面 ID 缓存到本地文件，解析失败时便于排查，不建设独立快照系统。

## 8. 关键风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| API Key 未获批或规则变化 | 无法稳定全量同步 | 先做 5–10 名选手的 MediaWiki API PoC；把数据访问集中在一个模块中，方便以后调整 |
| Wiki 模板和字段不统一 | 解析缺失、字段漂移 | 缓存响应；对关键解析器写少量样本测试；失败时在页面提示 |
| 选手重名、改名、同名页面 | 错误合并履历 | 使用来源页 ID 作为源标识，别名独立建表，实体合并必须可撤销 |
| 赛事与选手并非直接关联 | 履历覆盖率不足 | 从成绩表、赛事阵容、战队阵容多路径建立参与关系，并记录证据来源 |
| 许可或图片版权处理不当 | 合规风险 | 即使自用也保留来源；图片只远程显示，不批量分发 |
| 中文翻译不一致 | 搜索和阅读体验差 | 原文为主数据，译名进入别名表，建立术语表并允许人工修订 |

## 9. 里程碑与验收

### M0：数据可行性验证（1–2 个工作日）

- 申请 LiquipediaDB API Key，配置项目 User-Agent 和联系人。
- 抽取 5–10 名不同地区、不同时期的选手。
- 验证个人资料、战队历史、赛事成绩三类字段的覆盖率。
- 记录无法可靠获取的字段，随即确定最终页面字段。

验收：样本可重复导入，所有请求符合限流要求，核心字段覆盖率有量化结果。

### M1：可用版本（3–5 个工作日）

- 建立 SQLite 数据库、缓存目录和幂等 upsert。
- 实现选手、战队、赛事和参赛记录的同步。
- 实现搜索、筛选、选手详情和手动同步按钮。

验收：重复同步不产生重复数据；失败可定位并重试；任意字段能追溯来源。

### M2：补齐体验（2–3 个工作日，可选）

- 根据实际使用补充战队/赛事详情、排序或 CSV 导出。
- 增加简单备份脚本和自动更新任务（确有需要时再做）。

验收：实际使用中遇到的主要不便得到解决；没有明确需要时不继续扩展。

## 10. 工作量预估

数据接口可用的前提下，单人约 1–2 周可完成自用版。主要不确定性是 LiquipediaDB API 审批和赛事履历字段覆盖，不在界面与部署。

## 11. 立项前需要确认的决策

以下决策不阻塞 M0，但应在 M0 结束前确定：

- 首发语言仅中文，还是中英双语。
- 收录范围是全部选手，还是优先在役选手和 Tier 1/2 赛事。
- 是否允许展示实名、出生日期、社交账号和远程头像。
- 是否计划二期接入 OpenDota/STRATZ 的单局表现数据。
- 用于 API User-Agent 的项目名称与联系邮箱。
